# 파일럿 운영 안내 (B-36)

설치를 마친 quartz-admin에 사내 Quartz 스케줄러를 등록해 파일럿을 운영하고, [PRD §8](PRD.md) 성공 지표를 재는 방법입니다. 설치·백업·장애 대응은 [운영 런북](operations.md)을, 대상 DB 계정은 [db-accounts.md](db-accounts.md)를 보세요.

진행 순서는 다음과 같습니다.

1. 사내 스케줄러 인벤토리를 만든다(1장)
2. 파일럿 스케줄러를 고른다(2장)
3. 스케줄러마다 등록 점검표를 따른다(3장)
4. 등록한 날부터 성공 지표를 잰다(5장)

## 1. 사내 스케줄러 인벤토리

인벤토리는 "전 클러스터 등록" 지표의 분모입니다. 호스트·스키마 같은 사내 정보가 들어가므로 **이 저장소가 아니라 사내 위키나 공유 스프레드시트**에 둡니다.

### 1.1 찾는 방법

1. **서비스 담당자에게 묻기**: Quartz를 쓰는 서비스, 대상 DB, `quartz.properties`의 값(아래 표의 굵은 항목)을 받습니다.
2. **DB에서 찾기**: 담당자가 모르는 스케줄러가 있을 수 있으니 DBA가 Quartz 테이블 세트를 찾습니다. `SCHEDULER_STATE`로 끝나는 테이블 하나가 테이블 세트 하나입니다(앞부분이 prefix, 기본 `QRTZ_`).

   ```sql
   -- Oracle (DBA 권한. 없으면 ALL_TABLES로 보이는 것만)
   SELECT owner, table_name FROM dba_tables WHERE table_name LIKE '%SCHEDULER_STATE' ORDER BY owner;
   -- PostgreSQL (DB마다 실행)
   SELECT table_schema, table_name FROM information_schema.tables
    WHERE lower(table_name) LIKE '%scheduler_state' ORDER BY table_schema;
   -- MySQL, MariaDB
   SELECT table_schema, table_name FROM information_schema.tables
    WHERE lower(table_name) LIKE '%scheduler_state' ORDER BY table_schema;
   ```

3. **도구로 SCHED_NAME 확인하기**: 테이블 세트 하나에 스케줄러(SCHED_NAME)가 여럿일 수 있습니다. 읽기 전용 계정으로 접속을 등록하면 감지 결과에 SCHED_NAME 후보와 잡·트리거·노드 수가 나옵니다(등록하지 않아도 후보를 볼 수 있습니다). 이것을 인벤토리의 한 줄씩으로 옮깁니다.

### 1.2 양식

| 항목 | 예 | 설명 |
| --- | --- | --- |
| 서비스 | 정산 배치 | |
| 담당 팀·담당자 | 정산개발팀 | 알림을 받을 Slack 채널도 적어 두면 3장에서 씁니다 |
| 환경 | prod | 접속의 환경 라벨로 그대로 씁니다(`prod`, `stage`, `dev`). `prod`는 화면에 빨간 띠로 구분됩니다 |
| DB 종류·버전 | Oracle 19c | [TRD §5.1](TRD.md) 지원 범위와 대조합니다 |
| 스키마·prefix | `BATCH`·`QRTZ_` | |
| **SCHED_NAME** | `SettleScheduler` | `org.quartz.scheduler.instanceName` |
| **Quartz 버전** | 2.3.2 | |
| **클러스터** | 예 | `org.quartz.jobStore.isClustered` |
| **misfire 임계값** | 60000 | `org.quartz.jobStore.misfireThreshold`(ms). 3장에서 도구 설정에 그대로 넣습니다 |
| 노드 수 | 2 | 평소 떠 있는 노드 수 |
| 지원 여부 | 대상 | 대상 / 제외(사유) |
| 등록일 | 2026-11-20 | 도구에 등록한 날 |
| 비고 | | |

### 1.3 지원 범위 밖

다음은 "제외"로 적고 사유를 남깁니다. 지표의 분모에서 빼되, 제외한 수도 함께 보고합니다.

- **클러스터 모드가 아닌 스케줄러**(`isClustered=false`): 노드가 `SCHEDULER_STATE`에 체크인하지 않아 노드 알림이 맞지 않습니다. 또 노드가 DB 행 잠금을 쓰지 않아 도구의 제어와 노드의 실행이 엇갈릴 수 있습니다([PRD §10.1](PRD.md) 가정).
- **RAMJobStore**: DB에 상태가 없어 볼 수 없습니다.
- **지원하지 않는 DB 버전**: [TRD §5.1](TRD.md)의 최소 버전보다 낮은 DB입니다. Oracle 12.1~19c는 사내 점검([oracle-legacy-check.md](oracle-legacy-check.md)) 결과를 따릅니다.
- **Quartz 1.x**: 테이블 구조가 달라 지원하지 않습니다.

## 2. 파일럿 스케줄러 고르기

처음부터 전부 등록하지 않고 2~3개로 시작해 오탐과 운영 부담을 먼저 봅니다.

| 기준 | 이유 |
| --- | --- |
| 담당 팀이 협조적이다 | 오탐·누락을 바로 알려 줘야 알림 설정을 다듬을 수 있습니다 |
| 사내 주력 조합(Quartz 2.3.2, Oracle)을 하나 이상 넣는다 | 가장 많이 쓸 조합에서 먼저 확인합니다 |
| 운영 환경이 아닌 스케줄러를 하나 넣는다 | 제어 명령은 여기서 먼저 써 봅니다 |
| misfire나 노드 장애를 겪은 적이 있다 | 장애 인지 시간 지표를 실제 사례로 잴 수 있습니다 |

권장 단계:

| 단계 | 기간 | 대상 | 계정 | 확인할 것 |
| --- | --- | --- | --- | --- |
| 1 | 1주 | 운영 외 1~2개 | 쓰기 | 감지, 대시보드, 알림, 제어(일시정지·재개, 즉시 실행, 스케줄 수정) |
| 2 | 1~2주 | 운영 1~2개 | 읽기 전용 | 운영 부하, 알림 오탐, 장애 인지 |
| 3 | 이후 | 운영 | 쓰기 | 담당 팀이 동의한 스케줄러부터 쓰기 계정으로 바꿉니다(접속 수정에서 계정만 바꾸면 됩니다) |

각 단계를 넘어가기 전에 5장의 주간 점검을 한 번 해 보고 넘어갑니다.

## 3. 등록 점검표

스케줄러마다 이 순서로 등록합니다.

1. **DB 계정**: [db-accounts.md](db-accounts.md)의 SQL로 읽기 전용 또는 쓰기 계정을 만듭니다. 같은 DB의 스케줄러는 계정 하나를 같이 씁니다.
2. **나가는 연결**: 도구 호스트에서 대상 DB 포트로 나가는 규칙을 더합니다([운영 런북 5.1](operations.md)).
3. **접속 추가**: 접속 → 접속 추가. 환경 라벨은 인벤토리의 환경, 태그에는 담당 팀을 넣습니다. 스키마 칸을 빠뜨리지 않습니다([db-accounts.md](db-accounts.md) "접속 등록").
4. **감지와 등록**: 후보에서 인벤토리의 SCHED_NAME을 고르고 등록합니다. 잡·트리거·노드 수가 담당 팀이 아는 값과 맞는지 봅니다.
5. **스케줄러 설정**: 스케줄러 상세 머리글의 설정 버튼(또는 접속 상세의 스케줄러 줄 메뉴 → 설정)에서 확인합니다.
   - **misfire 임계값**을 인벤토리 값(애플리케이션의 `misfireThreshold`)과 같게 둡니다. 다르면 연체 알림이 너무 이르거나 늦습니다.
   - **기대 노드 수**는 등록할 때 감지한 활성 노드 수로 채워집니다. 등록 순간에 노드 하나가 내려가 있었다면 평소 노드 수로 고칩니다.
6. **알림 채널**: 등록하면 기본 규칙 6개(연체, 트리거 오류, 오래 BLOCKED, 노드 부족, 클러스터 다운, 감시 실패)가 인앱 채널로 만들어집니다. 담당 팀의 Slack 채널(채널 → 채널 추가, "테스트 발송"으로 확인)을 규칙에 연결합니다.
7. **지켜보기**: 15분쯤 두고 대시보드 카드가 정상이고 열린 알림이 없는지 봅니다. 평소에도 열려 있는 알림(늘 BLOCKED인 트리거 등)이 있으면 규칙의 적용 범위나 임계값을 조정하고, 조정한 이유를 인벤토리 비고에 적습니다.
8. **인벤토리 갱신**: 등록일을 적습니다.

담당 팀의 배포·점검으로 노드를 일부러 내릴 때는 스케줄러 상세의 **알림 음소거**(최대 7일)를 쓰라고 안내합니다.

## 4. 파일럿 중단과 되돌리기

도구는 대상 DB에 자기 테이블을 만들지 않으므로 등록을 지우면 흔적이 남지 않습니다.

1. 접속 상세의 스케줄러 줄 메뉴 → 등록 해제: 도구의 스케줄러 설정, 알림 규칙, 알림 기록만 지웁니다. 대상 DB의 Quartz 테이블은 건드리지 않습니다. 감사 로그는 남습니다.
2. 그 DB의 스케줄러를 모두 지웠으면 접속도 지웁니다.
3. DBA가 도구 계정을 지웁니다(`DROP USER`). 나가는 연결 규칙도 뺍니다.
4. 인벤토리의 등록일을 지우고 비고에 중단 사유를 적습니다.

## 5. 성공 지표 측정

### 5.1 지표별 측정 방법

| 지표 (PRD §8) | 목표 | 데이터 | 계산 |
| --- | --- | --- | --- |
| DB 직접 수정 제로 | 운영 1개월간 `QRTZ_` 직접 SQL 수정 0건 | 운영팀 자가 보고, 변경 요청 기록 | 월말에 팀별로 "이번 달 Quartz 테이블을 SQL로 직접 고친 건수와 이유"를 받습니다 |
| 전 클러스터 등록 | 사내 Quartz 2.x 스케줄러 100% 등록 | 인벤토리, 대시보드 | 등록 수 ÷ 지원 대상 수. 제외 수와 사유를 같이 적습니다 |
| 장애 인지 시간 단축 | 발생 5분 안에 알림, 사용자 제보보다 먼저 인지 90% 이상 | 알림 센터, 장애 기록 | 아래 5.2 |
| 제어로 인한 사고 없음 | 도구 제어로 인한 오동작·잠금 장기 점유 0건, 제어 감사 기록률 100% | 감사 로그 CSV, 장애 회고 | 아래 5.3 |

직접 수정이 0건이 아니면 이유를 나눕니다. 도구에 없는 기능 때문이면(예: CAL_INT 트리거 수정) 후속 작업 후보로 BACKLOG에 올리고, 도구로 할 수 있는 일이었다면 담당 팀에 사용법을 안내합니다. DBA가 DB 감사 기능(Oracle Unified Auditing, PostgreSQL `pgaudit` 등)을 이미 쓰고 있다면 `QRTZ_` 테이블의 DML 기록과 대조해 자가 보고를 보완할 수 있습니다.

### 5.2 장애 인지 시간

알림 센터(해소 탭, 또는 모두 탭)의 **발생** 열이 도구가 조건을 처음 본 시각입니다. 장애마다 다음을 기록합니다.

| 기록 | 어디서 |
| --- | --- |
| 실제 발생 시각 | 장애 기록. misfire는 놓친 실행 예정 시각, 노드 다운은 노드가 멈춘 시각(애플리케이션 로그·호스트 감시) |
| 알림 발생 시각 | 알림 센터의 발생 열 |
| 사용자 제보 시각 | 장애 기록(제보가 없었으면 비움) |

- **인지 지연** = 알림 발생 − 실제 발생. 5분 이하면 목표 달성입니다.
- **선인지율** = (제보가 없었거나, 알림이 제보보다 이른 장애 수) ÷ 전체 장애 수. 90% 이상이 목표입니다.
- 도구가 알림을 내지 않은 장애도 빠짐없이 적습니다. "알림 없음"이 개선할 거리입니다.

기본 설정에서 예상하는 인지 지연은 다음과 같습니다. 이보다 크게 늦으면 감시 주기나 스케줄러 설정을 확인합니다.

| 알림 | 조건이 성립하는 때 | 예상 최대 지연(감시 주기 60초 포함) |
| --- | --- | --- |
| 연체 | 실행 예정 시각 + misfire 임계값(60초) + 연체 유예(60초) | 약 3분 |
| 트리거 오류 | 상태가 ERROR가 된 때 | 약 1분 |
| 노드 부족, 클러스터 다운 | 마지막 체크인 + 체크인 간격 × 3(기본 체크인 간격 7.5초면 약 23초) | 약 1분 30초 |
| 오래 BLOCKED | BLOCKED를 처음 본 뒤 30분 | 30분 + 1분(장애 인지 지표에서는 뺍니다) |

해소된 알림은 `QA_ALERT_RETENTION_DAYS`(기본 90일)가 지나면 지워지므로 월말 보고 때 그달 장애의 알림 시각을 옮겨 둡니다.

### 5.3 제어로 인한 사고

감사 로그 → 기간을 고르고 "CSV로 내보내기"로 그달 기록을 받습니다(시각은 UTC).

- **제어 건수**: `작업` 열이 다음 중 하나인 줄입니다. `trigger.pause`, `trigger.resume`, `job.pause`, `job.resume`, `trigger_group.pause`, `trigger_group.resume`, `job_group.pause`, `job_group.resume`, `scheduler.pause`, `scheduler.resume`, `job.trigger`, `trigger.reschedule`, `trigger.delete`, `job.delete`
- **실패 검토**: `결과`가 `failure`인 제어를 봅니다.
  - `LOCK_TIMEOUT`: 노드가 잠금을 오래 잡고 있어 도구가 5초 만에 포기한 경우입니다. 도구가 잠금을 오래 잡은 것이 아닙니다. 같은 스케줄러에서 잦으면 담당 팀과 노드 상태를 봅니다.
  - `INTERRUPTED`: 작업 중 도구가 꺼져 결과를 모르는 기록입니다. 대상 상태를 확인했는지 적습니다.
  - `STATE_CONFLICT`: 화면에서 본 뒤 상태가 바뀌어 실행하지 않은 정상 거부입니다.
- **기록률**: 도구는 제어를 실행하기 전에 감사 기록을 먼저 남기므로([TRD §7.1](TRD.md)) 도구로 한 제어는 모두 기록됩니다. 장애 회고에서 "도구로 바꿨다"는 변경이 감사 로그에 없으면 그 건을 사고로 셉니다.
- **사고**: 장애 회고에서 원인이 도구의 제어인 건입니다. 0건이 목표입니다.

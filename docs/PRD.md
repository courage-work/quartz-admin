## 1. 배경과 문제

사내 여러 서비스가 Quartz Scheduler를 JDBC JobStore 클러스터 모드로 운영하고 있습니다. 스케줄러 상태는 Oracle, PostgreSQL, MySQL, MariaDB에 흩어진 `QRTZ_` 테이블에 저장되어 있습니다.

운영팀(DBA/SRE)이 겪는 문제는 다음과 같습니다.

- **제어 수단이 없음**: 배치를 잠시 멈추거나, 지금 한 번 돌리거나, cron을 바꾸려면 해당 서비스를 재배포하거나 운영 DB에 직접 SQL을 실행해야 합니다. 직접 SQL은 Quartz의 상태 전이 규칙과 잠금 규칙을 모르면 스케줄러 오동작으로 이어집니다.
- **흩어진 가시성**: 스케줄러마다 다른 DB 콘솔에 접속해야 상태를 볼 수 있습니다. 전체 클러스터 현황을 한 화면에서 볼 방법이 없습니다.
- **늦은 장애 인지**: misfire, ERROR 상태 트리거, 클러스터 노드 다운을 사용자 제보로 뒤늦게 알게 됩니다.

## 2. 목표와 비목표

### 2.1 목표

1. 운영자가 SQL 콘솔이나 앱 재배포 없이 Quartz 잡과 트리거를 **안전하게 제어**한다.
2. 사내 모든 Quartz 스케줄러를 **한 화면에서 조회**한다.
3. DB 상태로 판단할 수 있는 이상 징후를 **5분 안에 알림**으로 받는다.
4. 도구가 수행한 모든 변경을 **감사 로그**로 추적한다.

### 2.2 비목표 (MVP)

- 잡 실행 이력 수집과 조회 (Phase 2)
- 잡 실행 중 예외로 인한 실패 감지. Quartz는 잡 예외를 DB에 남기지 않으므로 애플리케이션 측 연동이 필요합니다 (Phase 2 이후).
- 새 잡 생성, JobDataMap 편집 (Java 직렬화 BLOB)
- SSO/LDAP 인증, 팀별 권한 분리, 승인 워크플로
- 관리 도구 다중 인스턴스 HA 구성
- 임의 SQL 실행 기능
- Quartz 1.x, Quartz 이외의 스케줄러

## 3. 사용자

| 페르소나 | 설명 | 주요 니즈 |
| --- | --- | --- |
| 운영자 (DBA/SRE) | 여러 서비스의 배치 인프라를 운영하는 소수의 사내 엔지니어 | 빠르고 안전한 제어, 전체 현황 파악, 장애 조기 인지 |
| 관리자 | 운영자 중 도구 자체를 관리하는 사람 | 사용자 계정 관리 |

외부 고객용 제품이 아니며, 사용자는 수십 명 이하로 가정합니다.

## 4. 핵심 개념

```
접속(Connection) ── 1:N ──> 스케줄러(Scheduler) ── 1:N ──> 잡(Job) ── 1:N ──> 트리거(Trigger)
                                     └── 1:N ──> 클러스터 노드(Instance)
```

| 용어 | 정의 |
| --- | --- |
| 접속 | 대상 DB 하나에 대한 접속 정보 (DB 종류, 호스트, 계정 등) |
| 스케줄러 | 접속 안에서 `테이블 prefix + SCHED_NAME` 조합으로 식별되는 Quartz 스케줄러. DB 하나에 여러 개가 있을 수 있음 |
| 클러스터 노드 | 같은 스케줄러를 공유하는 Quartz 인스턴스. `SCHEDULER_STATE` 테이블에 체크인 기록이 남음 |
| 환경 라벨 | 접속에 붙이는 `prod` / `stage` / `dev` 등의 구분. 화면 표시와 필터링에 쓰임(확인 절차는 환경과 관계없이 같음) |
| 읽기 전용 접속 | 쓰기 권한이 없는 계정으로 등록한 접속. 조회와 알림만 가능하고 제어는 불가 |

## 5. 주요 사용 시나리오

1. **배포 중 배치 일시정지**: 운영자가 서비스 배포 전에 특정 잡 그룹을 일시정지하고, 배포 후 재개한다.
2. **장애 후 수동 재실행**: 외부 연동 장애로 정산 잡이 처리되지 못했다. 운영자가 장애 복구 후 해당 잡을 즉시 실행한다.
3. **cron 변경 요청 처리**: 현업 요청으로 리포트 잡 실행 시각을 바꾼다. 다음 실행 시각 미리보기를 보고 저장한다.
4. **새벽 misfire 인지**: 트리거가 예정 시각을 지나도 발화되지 않아 Slack 알림을 받는다. 대시보드에서 원인(노드 다운, BLOCKED 등)을 확인한다.
5. **노드 다운 인지**: 클러스터 노드 하나가 체크인을 멈춰 알림을 받는다.
6. **신규 스케줄러 등록**: 새 서비스의 DB 접속을 등록한다. 도구가 prefix와 SCHED_NAME을 자동으로 찾아 제시하고, 운영자가 등록할 스케줄러를 고른다.
7. **변경 추적**: 장애 회고에서 "누가 언제 이 트리거를 멈췄는가"를 감사 로그로 확인한다.

## 6. 기능 요구사항

우선순위: **P0** = MVP 필수, **P1** = MVP 포함 목표(일정 부족 시 이월 가능), **P2** = 후속

### 6.1 접속·스케줄러 관리

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| FR-CON-01 | 접속 등록: DB 종류(Oracle/PostgreSQL/MySQL/MariaDB), 호스트, 포트, DB명 또는 Oracle 서비스명/SID, 스키마, 계정, 비밀번호, 이름, 환경 라벨, 태그를 입력해 등록한다. | P0 |
| FR-CON-02 | 연결 테스트: 저장 전에 연결을 시험하고, 실패 시 원인(네트워크, 인증, 권한, 타임아웃)을 구분해 보여준다. | P0 |
| FR-CON-03 | 자동 감지: 접속 시 카탈로그(`information_schema`, `ALL_TABLES` 등)를 조회해 Quartz 테이블 세트, 테이블 prefix, 실제 테이블명 대소문자, SCHED_NAME 목록, 스키마 버전 차이(선택 컬럼 존재 여부), 불리언 저장 형식을 감지한다. 감지 결과는 스케줄러 후보 목록으로 보여주고, 운영자가 등록할 스케줄러를 선택한다. | P0 |
| FR-CON-04 | 쓰기 권한 점검: 계정의 `QRTZ_` 테이블 쓰기 권한과 잠금 권한을 확인한다. 쓰기가 불가능한 계정은 읽기 전용 접속으로 등록하고, 운영자가 직접 읽기 전용으로 지정할 수도 있다. | P0 |
| FR-CON-05 | 접속 수정·삭제·재감지: 접속 정보를 수정할 때 비밀번호를 다시 입력하지 않으면 기존 값을 유지한다. 스키마가 바뀌면 재감지할 수 있다. 접속을 삭제하면 하위 스케줄러와 알림 규칙도 함께 정리되며, 삭제 전 영향 범위를 보여준다. | P0 |
| FR-CON-06 | 자격증명 보호: 비밀번호는 암호화해 저장하고, 화면, API 응답, 로그 어디에도 평문으로 노출하지 않는다. | P0 |
| FR-CON-07 | 스케줄러 설정: 스케줄러별 표시 이름, misfire 판정 임계값, 체크인 판정 배수, 기대 노드 수(등록 시 감지된 활성 노드 수로 자동 설정), 감시 주기 같은 감시 파라미터를 설정한다. | P0 |

**수용 기준 (FR-CON-03)**

- 4종 DB 각각에서 Quartz 2.x 공식 `tables_*.sql`로 만든 스키마를 감지한다.
- 기본 `QRTZ_` 이외의 prefix와 한 DB 안의 여러 prefix를 감지한다.
- 한 테이블 세트 안의 여러 SCHED_NAME을 각각 별도 스케줄러 후보로 제시한다.
- MySQL/MariaDB에서 `lower_case_table_names` 설정과 관계없이 실제 테이블명을 찾는다.

| FR-CTL-00d | 의미 동등성: 변경 결과(트리거 상태, 다음 실행 시각, 일시정지 그룹 기록)는 같은 조작을 Quartz `Scheduler` API로 했을 때와 같아야 한다. 예외: (1) 스케줄 수정(FR-CTL-06/07)은 개별 일시정지 상태를 유지한다(Quartz `rescheduleJob`은 해제함). (2) 그룹 단위 명령은 그룹 이름을 정확히 일치로 비교한다(Quartz는 `LIKE`로 비교해 `_`, `%`가 든 그룹 이름이 다른 그룹과 겹칠 수 있음). (3) 같은 결과를 보장할 수 없는 요청은 실행하지 않고 거부한다(FR-CTL-04). | P0 |
| FR-CTL-00e | 사전 상태 확인: 실행 직전에 대상의 현재 상태를 다시 읽는다. 화면에서 본 상태와 다르면 중단하고 최신 상태를 보여준다. | P0 |
| FR-CTL-00f | 모든 제어 시도(성공과 실패 모두)를 변경 전후 값과 함께 감사 로그에 남긴다. | P0 |

#### 기능

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| FR-CTL-01 | 트리거 일시정지/재개 | P0 |
| FR-CTL-02 | 잡 일시정지/재개: 잡에 연결된 모든 트리거에 적용 | P0 |
| FR-CTL-03 | 그룹 일시정지/재개: 트리거 그룹과 잡 그룹 단위로 적용. 트리거 그룹 일시정지는 이후 그 그룹에 추가되는 트리거에도 적용된다(`PAUSED_TRIGGER_GRPS` 반영). | P0 |
| FR-CTL-04 | 재개 시 misfire 처리: 도구는 상태만 전이하고 다음 실행 시각은 바꾸지 않는다. 예정 시각이 이미 지난 트리거는 Quartz 노드가 각 트리거의 misfire 처리 방식과 캘린더에 따라 최대 misfire 임계값(기본 60초) 안에 처리하며, 화면에 이를 안내한다. 일시정지된 트리거 그룹(또는 전체 일시정지) 안의 트리거를 개별로 재개할 때 예정 시각이 이미 지났으면, Quartz 노드가 다시 일시정지시키므로 실행하지 않고 그룹을 먼저 재개하라고 안내한다. | P0 |

## 7. 비기능 요구사항

### 7.1 보안

- **NFR-SEC-01**: 대상 DB 비밀번호는 AES-256-GCM으로 암호화해 저장합니다. 암호화 키는 환경변수나 시크릿으로 주입하며, 키가 없으면 도구가 기동하지 않습니다.
- **NFR-SEC-02**: 대상 DB에 실행하는 SQL은 도구에 미리 정의된 쿼리만 허용합니다. 사용자 입력은 항상 바인드 변수로 전달합니다.
- **NFR-SEC-03**: 로그와 오류 메시지에 비밀번호나 접속 문자열 원문을 남기지 않습니다.
- **NFR-SEC-04**: 외부 노출 시 HTTPS로 서비스합니다(리버스 프록시 종단 허용). 세션 쿠키는 `HttpOnly`, `Secure`, `SameSite`로 설정하고 CSRF를 방어합니다.
- **NFR-SEC-05**: SQLite 메타데이터 파일과 백업본은 민감 자산으로 취급합니다(파일 권한 제한).

### 7.2 규모와 성능

규모 가정: **스케줄러 최대 100개, 스케줄러당 트리거 최대 10,000개, 동시 사용자 20명 이하**

- **NFR-PERF-01**: 대시보드 첫 화면 p95 3초 이내. 연결 불가 스케줄러가 있어도 이 목표를 지킵니다(대상별 타임아웃).
- **NFR-PERF-02**: 트리거와 잡 목록은 서버 측 페이지네이션을 쓰며, 페이지 응답 p95 2초 이내(대상 DB가 정상 응답할 때).
- **NFR-PERF-03**: 알림 감시는 전체 스케줄러를 한 주기(기본 60초) 안에 점검합니다. 조건 발생부터 발송까지 최대 5분입니다.
- **NFR-PERF-04**: 대상 DB 부하 최소화: 접속당 커넥션은 최대 2개로 두고, 필요할 때 만들어 유휴 시 닫습니다. 감시 쿼리에는 실행 시간 제한을 둡니다. 쓰기 트랜잭션은 짧게 유지합니다.

### 7.3 안정성과 안전성

- **NFR-REL-01**: 대상 DB 하나의 장애나 지연이 다른 스케줄러의 조회와 감시를 막지 않습니다.
- **NFR-REL-02**: 도구가 비정상 종료되어도 대상 DB에 미완료 트랜잭션이나 잠금이 남지 않습니다.
- **NFR-REL-03**: 메타데이터 저장소(SQLite)는 WAL 모드로 운영하며, 백업과 복원 절차를 문서화합니다.
- **NFR-REL-04**: 도구는 단일 인스턴스로 운영합니다. 같은 데이터 디렉터리로 다른 인스턴스가 이미 실행 중이면 기동을 거부합니다.

### 7.4 호환성

- **NFR-COMP-01**: Quartz 2.x(2.0~2.5) 표준 스키마를 지원합니다. 버전별 컬럼 차이는 자동 감지로 흡수합니다.
- **NFR-COMP-02**: 대상 DB는 Oracle, PostgreSQL, MySQL, MariaDB 4종을 MVP부터 모두 지원합니다. 최소 지원 버전은 미결 사항(§11)에서 확정합니다.
- **NFR-COMP-03**: 임의의 테이블 prefix, 테이블명 대소문자, 불리언 저장 형식(`1`/`0`, `Y`/`N`, `true`/`false`)을 지원합니다. 값을 쓸 때는 기존 저장 형식을 유지합니다.
- **NFR-COMP-04**: 최신 Chrome, Edge, Safari 브라우저를 지원합니다.

### 7.5 배포와 운영

- **NFR-OPS-01**: Docker Compose로 단일 호스트에 배포합니다. 메타데이터는 Docker 볼륨 하나에 저장합니다.
- **NFR-OPS-02**: 설정(암호화 키, 초기 관리자, SMTP, 포트, 감사 로그 보존 기간)은 환경변수로 주입합니다.
- **NFR-OPS-03**: 도구 자체의 헬스체크 엔드포인트와 구조화 로그(JSON)를 제공합니다.
- **NFR-OPS-04**: 버전을 올릴 때 메타데이터 스키마를 자동으로 마이그레이션합니다.

### 7.6 사용성

- **NFR-UX-01**: UI는 한국어로 제공합니다.
- **NFR-UX-02**: `prod` 환경 스케줄러는 화면에서 시각적으로 구분합니다(색상, 배지).
- **NFR-UX-03**: 제어 결과(성공, 실패와 원인)를 바로 알려주고, 화면을 최신 상태로 갱신합니다.

## 10. 가정, 제약, 위험

### 10.1 가정과 제약

- 개발은 1인이 AI 주도로 진행하므로, 범위 통제와 자동화 테스트가 일정의 핵심입니다.
- 기술 스택은 Next.js(관리 UI), NestJS(API), SQLite(메타데이터)로 정해져 있습니다. 세부 기술 결정은 TRD에서 다룹니다.
- 대상 스케줄러는 JDBC JobStore 클러스터 모드(`isClustered=true`)이며, 잠금은 DB 행 잠금(`StdRowLockSemaphore`)을 쓴다고 가정합니다.
- Quartz 노드와 관리 도구 서버의 시계는 NTP로 동기화되어 있다고 가정합니다.

### 10.2 위험

| ID | 위험 | 영향 | 대응 |
| --- | --- | --- | --- |
| R1 | 직접 쓰기가 Quartz 상태 전이 규칙과 어긋남(ACQUIRED, BLOCKED 상태 처리 등) | 트리거 누락이나 중복 실행 | Quartz `JobStoreSupport` 소스를 기준으로 상태 전이를 재현. 4종 DB와 실제 Quartz 클러스터를 띄운 통합 테스트 |

## 부록 A. 용어

| 용어 | 설명 |
| --- | --- |
| misfire | 트리거가 예정 시각에 발화하지 못한 상태. Quartz는 `misfireThreshold`(기본 60초)를 넘으면 misfire로 처리 |
| BLOCKED | 동시 실행 금지 잡이 실행 중이어서 같은 잡의 다른 트리거가 대기하는 상태 |
| ACQUIRED | 노드가 발화 직전에 트리거를 획득한 상태 |
| 체크인 | 클러스터 노드가 `SCHEDULER_STATE`에 주기적으로 생존을 기록하는 동작 |
| `QRTZ_LOCKS` | 클러스터 노드 간 상호 배제에 쓰는 잠금 테이블(`TRIGGER_ACCESS`, `STATE_ACCESS` 행) |
